# Flow graphs

Conventions for the mermaid flow graphs that map an act and its sessions — the bird's-eye view of
what happens when, which fights and decisions sit where, and which branches the party is likely to
take.

Read once per task when generating or editing a flow graph set. Generated by `/flow`
(`.claude/commands/flow.md`); commitment coverage is reported by `scripts/flow-status.py`.

**These are not gantt charts.** `meta/events.md` and `meta/calendar-template.md` cover the timeline
gantts built by `scripts/timeline-gantt.py` — different chart type, different rules. Nothing here
applies to those.

**Examples below are generic on purpose.** A flow graph set usually lives under a gitignored
workshop directory, and `workshop/CLAUDE.md` forbids writing workshop-derived content to tracked
paths without an explicit graduation step. Illustrate conventions with placeholder ids, never with
beats lifted out of a live draft.

## What a flow graph set is

A folder of markdown files under the act's working directory, one mermaid graph per file:

```text
<act-dir>/notes/<act-slug>-flow/
  README.md                      index, legend, id scheme, open items
  00-act-spine.md                the act: sessions as subgraphs, plus act-wide overlays
  01-session-1-<slug>.md         one file per designed session
  02-session-2-<slug>.md
  ...
  NN-payoff-slots.md             undesigned slots, if the season has room
```

**One graph per file.** A single file holding every graph renders each one small and makes them
compete for width. Splitting is the whole reason the set exists as a folder.

**Repo files, not artifacts.** The DM reads these zoomed in, side by side with the drafts they map.
Publish one only when it is being handed to someone outside the repo, and even then the repo file
stays the source.

### The per-session snapshot

A planned session also carries its own chart, in its own folder:

```text
scheduler/sessions/Session {NN} {Name}/_flow.md
```

That file is the session's graph only — not the act spine, not the other sessions — and it travels
with the plan when `/recap` moves the folder to `historian/`. It is a **graduated snapshot** of the
matching file in the act's set, so the set stays the live source and the one `flow-status.py`
reads. The `_` prefix keeps it out of `validate.ps1`'s entity checks and the semantic index; it
carries no frontmatter and is never an entity.

Because there are two copies, they drift. Regenerate the snapshot with `/flow --session {NN}`
rather than hand-editing both, and never let the snapshot be the only place a marker moved.

## Node ids

**Every node prints its own id in its label, and the printed id is the literal mermaid node id.**
That is what makes a beat nameable out loud, in a message, and in a grep:

```powershell
rg "S1_EXAMPLE" <act-dir>/notes/<act-slug>-flow/
```

Prefixes:

- `ACT_` — act-wide: the act's opening state, an overlay that spans every session, the payoff region
- `S1_` … `SN_` — beats inside session N
- a topical prefix for a discoverable chain that crosses sessions, named for the chain itself
- `PAY_` — the undesigned payoff slots

Slugs are short, uppercase, speakable, and name the beat rather than describing it. Two words when
one will not do.

**A beat that appears at two zoom levels keeps one id.** The act spine and the session file draw the
same beat coarse and fine; they share the id. Where a session file needs finer grain than the act
spine, it **splits into new ids rather than renaming** — one act-level node opens up into several
session-level ones, and the act-level id stays on the summary node.

When a beat is cut or renamed, change the id everywhere it appears. The grep above finds all of
them.

## Commitment markers

Every node carries a marker **before** its id, so the chart doubles as the readiness tracker:

- `[x]` — **committed.** The DM has personally approved this beat, it is provisioned with notes, and
  it is ready to run under this repo's rules and structure.
- `[-]` — **draft.** Derived from workshop material or proposed by the engine. Plausible, not
  approved.
- `[?]` — **open.** A decision or a design gap. Cannot be committed until it is resolved — this is
  the marker for anything waiting on a player's backstory, a group vote, or a DM call.

A node definition therefore reads:

```text
S1_EXAMPLE["[-] S1_EXAMPLE<br/>what the beat is<br/>the detail that makes it runnable"]
```

### The commit gate

A node may be marked `[x]` only when **all four** hold:

1. **The DM said so.** Explicit approval of that beat, in conversation or in a decisions log.
2. **Notes exist.** A backing source the session can actually be run from — a beat sheet, a statblock
   note, a scheduler mission, a voice brief. Not "the idea is clear."
3. **No open upstream.** Every node that must happen before it is `[x]` too. A committed beat
   downstream of a `[?]` is a lie; mark it `[-]` until the blocker clears.
4. **Repo-conformant.** The entities it names exist (or are deliberately `exists: false` scheduler
   artifacts), the difficulty is set where the structure expects it, and the loot obligation in
   `meta/rewards.md` is answered if the beat is a reward beat.

**The engine never self-commits.** Claude may *propose* that a node now meets the gate and ask — it
may not flip `[-]` to `[x]` on its own judgment. Flipping to `[?]` or back to `[-]` when something
breaks is allowed and expected: a committed beat whose backing note gets contradicted by canon drops
to `[-]` with a line saying why.

### The commitment ledger

Each file ends with a **Commitment ledger** section: one bullet per `[x]` node naming the node id
and the backing source that satisfied gate item 2. Bullets, not a table.

```markdown
## Commitment ledger

- `S1_EXAMPLE` — backing note at `<path>`; approved `<date>`
```

Nodes at `[-]` or `[?]` do not appear in the ledger. An empty ledger is honest and normal for a
freshly generated set — say "nothing committed yet" rather than omitting the section.

## Node kinds

Seven classes, by what the beat *is*. Colors set `fill`, `stroke` **and** `color` so they survive
both light and dark renderers:

```text
classDef combat   fill:#F6DCD3,stroke:#B4452A,color:#5A1E10
classDef social   fill:#E6E3D5,stroke:#8C8463,color:#3D3A28
classDef decision fill:#FDF0CE,stroke:#C79A2B,color:#5A4410
classDef stake    fill:#D9E8DC,stroke:#4F8060,color:#1F3D2A
classDef seed     fill:#DCE3EF,stroke:#5E7296,color:#24334D
classDef fail     fill:#EFE2E2,stroke:#A3736E,color:#4A2C29,stroke-dasharray:4 3
classDef open     fill:#EDEAE6,stroke:#9A948C,color:#4A453F,stroke-dasharray:4 3
```

- **combat** (rust) — a fight, or a combat-resolution beat like a morale break
- **social** (parchment) — roleplay, town, travel, any scene played in conversation
- **decision** (lantern) — a real fork, drawn as a diamond `{"..."}`
- **stake** (green) — a stake tick, loot, or mechanical payoff
- **seed** (river blue) — a thread planted or paid off
- **fail** (dusty red, dashed) — a designed setback or fail floor. Designed, so it is not `open`
- **open** (grey, dashed) — undesigned, or an open DM decision. Pairs with the `[?]` marker

Declare only the classes a given graph actually uses; an unused `classDef` makes the legend lie.

The marker and the class are **independent axes**. A combat node can be `[x]`, `[-]`, or `[?]`; it
stays rust in all three. Only genuinely undesigned beats take the `open` class — a documented
botch path is `fail`, not `open`.

## Drawing rules

**Diamonds at real forks only.** A decision node earns its shape when the design actually branches
and both outcomes are drawn. "The party might talk to someone" is not a fork. A choice the party
cannot have both halves of is.

**Fail states are paths, not dead ends.** Draw where a botch leads and route it back into the spine,
with the edge labeled so the consequence is legible. A graph with no outbound edge from a failure
node is asserting a dead end the act probably does not have.

**Convergent outs.** Where several approaches reach the same objective — talk, trick, intimidate,
fight — draw them all converging on one node. That is what proves none of them costs the party the
payoff.

**Overlays are dotted.** A thread that runs alongside the spine rather than through it — a dormant
relic, a discoverable chain, a recurring antagonist — connects with `-.->` so the spine stays
readable as the spine.

**Act spine uses subgraphs**, one per session, `flowchart LR`. Session files use `flowchart TD`.

## Honesty rules

These graphs get planned off, so they must not overstate what exists:

- **Mark what is inferred.** A session with no beat sheet says so in prose above its graph, names
  what it was drawn from, and leans on `[-]` and `[?]`.
- **Never invent design to fill a gap.** An undesigned slot is drawn as one `open` node listing what
  it owes, not as invented beats.
- **Open levers belong to their owner.** A beat waiting on a player's backstory is `[?]` and stays
  `[?]` until that player fills it. Do not propose answers for them.
- **Contradicted canon wins.** When a graph disagrees with the historian, the graph is wrong. Redraw
  it and say so in the file's open-items list.

## Maintenance

The graph set is a derived view. When the source drafts change, the graph lags — treat it like any
other drift-prone state:

- `/flow` regenerates a set, preserving existing markers and ledger entries by node id
- `uv run scripts/flow-status.py` reports commitment coverage per file and flags committed nodes
  whose upstream is not committed
- A set living under a gitignored working directory is **local only**. If it needs to survive a
  clone, graduating it is a deliberate DM step, subject to the same gate as any other workshop
  content.
